# Deploying the new nepsdwarka.com

A handover guide for the tech team. The whole website, with its source code, is in this repository:
**https://github.com/priyaverma000-ai/neps-website**

A working preview runs on GitHub Pages: https://priyaverma000-ai.github.io/neps-website/

## 1. What the site is

- **Static HTML, CSS and JavaScript.** No database, no PHP, no framework. Any web server can host it (Apache, Nginx, IIS, or a static host such as Netlify or Cloudflare Pages).
- **Built pages live in the repository root** (`index.html`, `fee-structure.html`, and so on). The server only needs to serve these files.
- **Page sources** are in `src/tpl/`. `src/build.ps1` combines them with the shared header and footer and writes the finished pages. Developers edit `src/tpl`, never the root `.html` files.
- **Blog and news** are Markdown files in `content/blog/` and `content/news/`. Staff write them in a web editor at `/admin/` (Decap CMS). Publishing saves the file to GitHub, and a GitHub Action (`.github/workflows/build.yml`) rebuilds the pages within about a minute.
- **Forms** send enquiries to the admission team on WhatsApp (+91 98705 52633). No form data is stored on the server.

| Path | What it is |
|---|---|
| `*.html` | Finished pages, generated by the build. Don't edit by hand |
| `blog.html`, `blog-*.html` | Parent Journal list and one page per post (generated from `content/blog`) |
| `news.html`, `news-*.html` | School News list and one page per item (generated from `content/news`) |
| `admin/` | The blog and news editor (Decap CMS) and its settings, `admin/config.yml` |
| `content/` | Blog and news posts as Markdown |
| `css/`, `js/`, `images/`, `video/`, `docs/` | Styles, scripts, photos, the campus tour video and PDFs |
| `images/uploads/` | Images uploaded from the editor |
| `src/` | Page sources, FAQs (`faqs.json`) and the build script |
| `.htaccess` | Apache rules: https, pretty addresses, old blog redirects, caching |
| `deploy/nginx.conf` | The same rules for Nginx |
| `deploy/robots.production.txt` | The robots.txt to use on the live domain |

## 2. Put it on the school's server

### Option A (recommended): the server pulls from GitHub

This keeps the live site in step with the blog editor automatically.

1. On the server, clone the repository into the web root:
   `git clone https://github.com/priyaverma000-ai/neps-website.git /var/www/nepsdwarka`
2. Point the domain's document root at that folder.
   - **Apache:** `.htaccess` is already in the folder. Make sure `AllowOverride All` and `mod_rewrite` are on.
   - **Nginx:** copy `deploy/nginx.conf` into your server config and set `root`.
3. Pull updates every few minutes with a cron job:
   `*/5 * * * * cd /var/www/nepsdwarka && git pull --quiet`
   (Or trigger `git pull` from a GitHub webhook if you prefer instant updates.)
4. The `.htaccess` and Nginx rules already block `/src`, `/content`, `/deploy`, `/.git` and `/.github` from the web.

### Option B: push from GitHub to the server

Add a deploy step to `.github/workflows/build.yml` that copies the site to the server over SSH (rsync) or FTP after each build, using repository secrets for the server login. Also run it on pushes to `main` from developers.

### Option C: upload once by hand

`NEPS Website - Deploy Package.zip` holds a ready-to-upload copy of the site, with the production robots.txt already in place. Unzip it into the web root. With this option, blog and news posts published from `/admin/` will **not** reach the server until you upload again, so use A or B for the long term.

## 3. Go-live checklist

1. **robots.txt:** replace `robots.txt` with `deploy/robots.production.txt`. The current file blocks search engines on purpose, because it protects the GitHub Pages preview.
2. **Domain and https:** point nepsdwarka.com (and www) to the server and install an SSL certificate (Let's Encrypt is fine). The rules force `https://nepsdwarka.com`.
3. **Pretty addresses:** every page's Google address has no `.html` (for example `https://nepsdwarka.com/fee-structure`). The `.htaccess` and Nginx rules serve `fee-structure.html` for it. Test a few after launch.
4. **Old addresses:** old blog posts (`/blog/<post>`) redirect to the new ones. Check Google Search Console for other old addresses with traffic (for example `event-detail.php?gal_id=...` gallery pages) and add 301 redirects for them. A few pages still link to old gallery pages on the current site; replace those links when the old site goes.
5. **Google Search Console:** verify the domain and submit `https://nepsdwarka.com/sitemap.xml`.
6. **Test:** open the site on a phone and check the menu, the enquiry and visit forms (they open WhatsApp), the fee finder and the age calculator.
7. **Keep the preview hidden:** once the live site is up, you can turn off GitHub Pages (Settings > Pages) or leave it with the blocking robots.txt.

## 4. Turn on the blog and news editor (one-time)

The editor is at `https://nepsdwarka.com/admin/`. Staff sign in with their GitHub account. GitHub login needs a small OAuth helper, because a static site can't hold the secret:

1. On GitHub: **Settings > Developer settings > OAuth Apps > New OAuth App** (create it under the school's account).
   - Homepage URL: `https://nepsdwarka.com`
   - Authorization callback URL: the callback address of the helper below.
2. Deploy a Decap-compatible GitHub OAuth helper with the app's Client ID and Client Secret, for example on Cloudflare Workers (free) or on the school's own server. Decap CMS's documentation lists ready-made ones under "External OAuth Clients".
3. In `admin/config.yml`, uncomment `base_url:` and set it to the helper's address. Commit and push.
4. Give each editor a GitHub account with **Write** access to the repository: **Settings > Collaborators > Add people**.

If you host on Netlify instead, you can skip the helper: turn on Netlify's GitHub OAuth provider and leave `base_url` out.

**Testing locally without GitHub:** run `npx decap-server` in the repository folder, serve the site (`src/serve.ps1` or any static server), and open `/admin/`. `local_backend: true` is already set.

### How staff publish a post

1. Open `/admin/`, sign in, choose **Parent Journal (blog)** or **School News**, then **New**.
2. Fill in the title, date, category, a one-line summary and a cover image, then write the post.
3. Press **Publish**. The site updates in one to two minutes. The newest posts also appear on the home page.
4. To take a post down, tick **Hide this post (draft)** and publish, or delete it.

## 5. Editing the rest of the site (developers)

1. Edit the page in `src/tpl/` (shared parts start with `_`). Page FAQs are in `src/faqs.json`.
2. Build: `powershell -ExecutionPolicy Bypass -File src/build.ps1` on Windows, or `pwsh src/build.ps1` on Linux and macOS (PowerShell 7).
3. Preview: `powershell -File src/serve.ps1`, then open http://localhost:8765 (or any static server in the repository root).
4. Commit and push the source and the built pages together. Run `git pull` first, because the editor may have added posts.

The first line of each page in `src/tpl` holds its Google title, description, address, share image and breadcrumb name, separated by `||`.

## 6. Content still to come from the school

Unfilled sections are marked `DRAFT SLOT` in the source and are **hidden on the site**. Add `?drafts=1` to any page address to see them (for example `/safety?drafts=1`). Fill them in `src/tpl/`, delete the draft box, and rebuild.

|---|---|
| Mandatory disclosure | 2026-27 disclosure PDF, affiliation number, school code, principal, CBSE tables (CBSE requires these) |
| Safety and wellbeing | CCTV and gate rules, medical room and first aid, fire drills, child protection policy, poor-air-day plan |
| Contact | Office hours, and one admission phone number for the whole site |

| Clubs and houses | The rest of the 2026-27 student council |
| Primary, Middle school | Class sizes, subjects per class, third language |
| Robotics and AI | Lab photo, kit cost, what is taught in each class |

| Gallery, Circulars | 2026-27 photo albums with captions, new circulars |

Also confirm before launch: parent consent to show students' names and photos (results, sports, student council) and alumni consent.
